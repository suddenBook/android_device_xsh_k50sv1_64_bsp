E-087 artifact: persist.vendor.mtk_wfc_support is MediaTek's master gate for the
RIL -> MAL data-call notification, and it is why VoLTE stopped at E-086's line
================================================================================

1. The gate, read out of the binaries
--------------------------------------
libmtkconfig.so `mtkGetFeatureByOs(id, buf)` (0x3028) is a 9-way switch whose
jump table is at file offset 0x19c8 (bytes 00 21 09 12 05 2c 30 1d 34). Decoded:

  id 0 -> property_get("persist.radio.multisim.config", default "dsds")
  id 1 -> literal "1"
  id 2 -> literal "1"
  id 3 -> literal "1"
  id 4 -> property_get("persist.vendor.volte_support",      default "0")
  id 5 -> property_get("persist.vendor.vilte_support",      default "0")
  id 6 -> property_get("persist.vendor.mtk_wfc_support",    default "0")
  id 7 -> property_get("persist.vendor.viwifi_support",     default "0")
  id 8 -> property_get("persist.vendor.mtk_rcs_ua_support", default "0")
  id > 8 -> return 0

libmtkrilutils.so `isEpdgSupport()` (0xd420) is exactly

  mtkGetFeature(6, buf); return buf[0..1] == '1';

so isEpdgSupport() IS `persist.vendor.mtk_wfc_support == "1"`, nothing else.

2. What that gate actually controls
------------------------------------
mtk-ril.so `responseUnsolDataCallRspToMal` (0xa9fe0) -- the ONLY function in the
RIL that calls `mal_datamngr_set_data_call_info{,_tlv}` -- opens with

  0x000a9fe0  sub sp, sp, 0x90
  ...
  0x000aa010  bl  isEpdgSupport
  0x000aa014  cbz w0, 0xaa1ec      ; -> function epilogue, MAL never told

All ten of its call sites are themselves inside isEpdgSupport-gated blocks
(requestSetupDataCallOverIPv6 0x91098, requestSetupDataCallEmergency,
requestSetupDataCallFallback, requestSetupDataCallOverEpdg,
requestReuseImsDataCall). The notification is doubly gated.

MediaTek reuses the same feature bit for 36 sites across the whole data path,
including rilSimMain, onMalPsStateChanged, requestSetupDataCall,
registerMalRestartCallbacks and configEpdg. It is not a VoWiFi-only switch; it
is the ePDG-capable RIL build flag, and the AP-driven IMS PDN path lives behind
it.

3. The port had it off in two places; stock has it on
-----------------------------------------------------
  stock  /vendor/build.prop:121                 persist.vendor.mtk_wfc_support=1
  port   device .../vendor.prop:39              persist.vendor.mtk_wfc_support=0
  port   .../init.mt6755.rc:350  setprop persist.vendor.mtk_wfc_support 0

The zero came from a coherent-looking but unverified premise -- "every WFC/video
capability is off, because VoWiFi is deferred" (vendor.prop:6-8). Nobody checked
what read it. That is HANDOFF trap 14 in its exact stated form.

5. The next boundary, and why it is the same subsystem
-------------------------------------------------------
  RIL-DATA: [getImsParamInfo] Call mal_datamngr_get_ims_info_tlv success
  RIL-DATA: dump defaultBearerVaConfig QOS[qci=5,...]
            flag[emergency_ind=0, pcscf_discovery_flag=1, signalingFlag=1,
                 assigned_rat=0]
  RIL-DATA: [queryEpdgRat] EPDG is not supported
  RIL-DATA: epdgConfig, isHandOver: 0, eran_type: 0
  MAL-IMSM: pdn cnt = 1, eran_type = 0, if_name = ccmni4
  MAL-IMSM: rat error!!                       (imsm_handler.c:4085)
  MAL-IMSM: pcscf_v4 : num = 0 ... addr = 0.0.0.0
  MFI-NWMNGR: status = 1, rat_type = 0, plmn = , lac = , ci = , cell_id = ,
  MAL-IMSM: get cell info fail, need retry    (imsm_handler.c:4141) x2866
  DC-ims  : [0] ActiveState msg: MSG_ID_WRAP_IMSM_IMSPA_PDN_ABORT   (T+78 s)

mtk-ril.so `configEpdg` (0xa9400) is the source of eran_type:

  if (pReq && isEpdgSupport() && isImsSupport())
        eran_type = pReq->assigned_rat;      /* = 0, from MAL */
  else  eran_type = 1;                       /* hardcoded cellular */

assigned_rat comes back 0 because MediaTek's RAT Decision Service never decides.
libmal_rds.so refuses, every ~5 s, 126 times in one boot:

  MAL-RDS: (ru_ims_ctrl_send_atcmd, 1587) [RDS-W][RU] MDmngr(1) or Epdgs(0) is not ready
  MAL-RDS: (ru_check_imsrat, 8837)        [RDS-W][RU] MDmngr(1) or Epdgs(0) is not ready

The two flags are fields of one RDS context: MDmngr at +0xac8, Epdgs at +0xacc.
Read at 0x1159d4/0x1159e0 (ru_check_imsrat) and 0xdc070/0xdc1ac/0xdc2ec/0xdc42c
(ru_ims_ctrl_send_atcmd). A full ARM PC-relative reference reconstruction over
the whole .text finds exactly ONE writer of +0xacc:

  000e8d10 <rds_ru_set_uiparam_req>:
    ...
    e939c: movw r0, #0x1
    e93a4: str  r0, [r1, #0xacc]      ; Epdgs = 1, unconditional

So Epdgs becomes ready only when something sends RDS a set-uiparam request.
`rds_set_ui_param` is exported as a FUNC by libmal.so (32- and 64-bit) and is
NOT among the 24 MAL APIs mtkrild resolves at init. On stock the caller is the
framework service `com.mediatek.wfo.impl.WifiOffloadService`, published as the
binder service "wfo" by `WfoService.makeWfoService()` in
/system/framework/mediatek-wfo-legacy.jar, which MediaTek's SystemServer starts.
Stock runs the whole chain: init.svc.mtk_hal_wfo=running, init.svc.wfca=running,
init.svc.vendor.epdg_wod=running, vendor.ril.epdg.interface.ctrl=1, and a full
set of vendor.ril.volte.mal.* parameters that this port has none of.

This supersedes E-085 section 4's verdict that the RDS Epdgs block "sits on a
different path". It sits on the VoLTE path. E-085 was right that mtk-ril sends
AT+EIMSVOLTE=1 itself; it was wrong to conclude from that that RDS did not
matter, because what RDS withholds is the IMS RAT, not the VoLTE enable.

6. Rejected on measurement
---------------------------
persist.net.wo.debug.rdsrat -- libmal_rds.so reads it in a helper at 0x111684
(legacy_rds_property_get + atoi) called from rds_ru_get_rpl_ind at 0x10e908 and
0x111828; a non-zero value takes a branch at 0x110e24 that writes the value into
all seven RPL entries' eran_type_ims/_mms instead of the computed 0xfe/0xff.
Set to 1 (both persist.net.wo.* and persist.vendor.net.wo.* spellings) and
rebooted: the "assigned ran" log never appeared and eran_type_ims stayed 254, so
the debug branch was not taken. Not pursued further: the slot-0 SIM came up
PIN_REQUIRED on that boot, so the run also could not have reached IMS. This is
an untested lever, not a refuted one.
