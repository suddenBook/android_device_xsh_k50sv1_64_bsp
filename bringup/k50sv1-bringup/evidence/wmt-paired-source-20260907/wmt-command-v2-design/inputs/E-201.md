# E-201 — untagged WMT command response boundary, 2026-09-06

Status: confirmed protocol limitation; no production repair is claimed. Kernel
commit `f89fb2920b9` adds characterization tests and documentation on top of
`5f2194a7f8c`.

After command A times out or is cancelled, a delayed untagged `ok` can complete
command B after B has been read by the launcher. The same ambiguity occurs when
A succeeds and its response is duplicated after the next command is delivered.
Five source-derived cases demonstrate incorrect completion with the current ABI.

The harness checks ten command histories twice: against actual producer,
broker, cancellation and character-device functions, and against a test-only
per-open generation model. All **20 expected observations** match under
ASan/UBSan. This is successful characterization, not a passing repair test.
The model rejects two cases involving different opens but still accepts all
three ambiguous same-open cases. Normal success/error, short reads, copy faults
and retry behavior serve as controls.

The installed product retains the original `wmt_launcher` ELF; the source
`wmt_loader` handles a different device initialization interface. No faithful
launcher source/module is present in the local device, vendor or native source
provider inventory. A complete repair needs the broker and launcher to exchange
and validate transaction identifiers together while preserving patch discovery,
version update and transport setup behavior. Switching only the kernel would
break compatibility; leaving an untagged fallback would retain the ambiguity.

[Characterization and source hashes](wmt-command-identity-20260906/characterization.json)
and [product compatibility inventory](wmt-command-identity-20260906/compatibility.json)
record the boundary. No responses were injected on the handset. Installed normal
startup exchanges are separate evidence and cannot disprove this failure path.

## Paired-launcher contract investigation, 2026-09-07

Offline analysis of the unchanged ELF, its compressed mini-debug symbols, the
two retained patch headers and existing build-16 logs now establishes the
MT6755/BTIF startup contract. The command table has `srh_patch` and
`srh_rom_patch`. Main reads, dispatches and replies serially; the startup power
ioctl runs on a separate thread. The original reply still contains no command
identity. No ELF execution, device response injection or replacement is part
of this investigation.

The MIT [OpenMTTools source](https://gitlab.com/Dahrkael/openmttools) is pinned
locally at `ef35f769d211a2942a6783410b58bd824dd363f9`. It supplies useful
metadata-layout reference but cannot replace this launcher unchanged. It lacks
MT6755 acceptance, the current `-o 1` argument, Android properties and the
driver-ready wait. Its power argument is 1, whereas this product's invocation
uses 2; those have different semantics in the paired kernel. Its firmware
comparison checks 16 bits, while the original checks only the low byte.

The observed search selects `ROMv2_lm_patch`, firmware `0x8a00` and two records.
The 28-byte header carries count and sequence at byte 24. The kernel receives
264-byte records containing the one-based sequence, four address bytes and
basename, then downloads in sequence order. Asynchronous `formeta.ready=yes`
and `patch.version=20200629194517a` publications do not prove download completion.
Short reads, inconsistent metadata and ioctl failures need explicit acceptance
tests when building the paired source implementation.

`srh_rom_patch` exists in the original, although this MT6755 boot and firmware
inventory do not demonstrate its use. The kernel's conditional
`update_patch_version` command exists in neither launcher table. Another client
can enable its condition through vendor-table/active-version ioctls, so it is
not intrinsically unreachable on MT6755. These boundaries must remain explicit
when defining replacement coverage.
