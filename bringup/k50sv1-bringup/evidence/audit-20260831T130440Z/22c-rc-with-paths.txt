#
# /vendor/bin/hw/android.hardware.sensors@2.0-service DT_NEEDEDs libpower.so

# HAL 2.0 contract gives the implementation a WakeLockQueue and expects it to
# hold a wake lock while a WAKE_UP sensor's events are in flight.
#

#

#     service.cpp:296 keeps capabilities across the uid change only
#     `if (capabilities_ && uid_)`, so the setuid(system) at :320-324 drops

#     group, not the capability.

# which this HAL does not implement and this chassis has no hardware for.
#

# on this SoC.
#
# The SELinux half is sepolicy/vendor/hal_sensors_default.te's wakelock_use();
# AOSP's public/hal_sensors.te does not grant it, so both halves are
# device-owned. Under Tier 1 the DAC failure is the visible one; under Tier 2
# the missing policy would be too.

@@FILE /vendor/etc/init/init.connectivity.modules.rc
# wmt_drv.ko creates /dev/wmtdetect and /dev/stpwmt, which wmt_loader opens.
#
# `on boot`, and it stays there. An earlier revision moved it to `on post-fs`
# to buy back a measured 926 ms of wmt_loader retry spin
# ("chipId detect failed, retrying, left retryCounter:%d" inside the blob),
# then reverted it when 5 GHz disappeared. Both the move and the revert were
# reasoned from a number that does not mean what it looked like:
#
#   * the spin happens inside wmt_loader, which is `class early_hal` and
#     `oneshot`. init forks it and does not wait, so the 926 ms is wall-clock
#     concurrent, not serial boot time. Measured on the current build,
#     `on late-fs` hands off to `on post-fs-data` 13 ms later.
#   * the `exec ... insmod` itself blocks init's action processing for 79 ms.
#     Moving it one stage earlier moves the same 79 ms earlier. Net serial
#     saving: ZERO.
#   * nothing on the boot-completed path consumes vendor.connsys.driver.ready.
#     Its only consumers are the four insmods below and wlan_assistant, and the
#     chip is not touched at all until the framework enables Wi-Fi at t=16.8 s,
#     13 s after this chain finishes. sys.boot_completed lands at t=26.0 s and
#     is bootanim-bound.
#
# So there is nothing to win here, and the ordering question that cost a Wi-Fi
# band was never really about NVRAM at all. See E-047.
on boot
    exec u:r:vendor_modprobe:s0 -- /vendor/bin/insmod /vendor/lib/modules/wmt_drv.ko

# wlan_assistant is NOT started from here.
#
# It is a `class main` service with no `disabled` (init.wmt.rc), so init starts
# it with its class and the binary blocks on its own two unbounded poll loops
# until /dev/wmtWifi and the NVRAM record both exist. That is the whole
# dependency, expressed where the daemon can actually enforce it rather than
# where init has to guess.
#
# What was here before was `on property:vendor.connsys.driver.ready=yes &&
# property:vendor.service.nvram_init=Ready -> start wlan_assistant`, and BOTH
# halves were wrong:
#
#   * The NVRAM half gated on nothing real. The WIFI record is FACTORY content
#     on the nvdata partition -- mtime 2026-01-13, unchanged across boots,
#     while BT_Addr in the same directory is rewritten every boot -- so
#     nvram_daemon neither creates nor touches it. It is readable from
#     `mount_all` at `on fs` (init.mt6755.rc:27), ~300 ms before `on post-fs`
#     and ~800 ms before this insmod. There was never a window in which it was
#     missing. Separately, vendor.service.nvram_init=Ready is published 10 s
#     (17.7 s on a fresh /data) BEFORE nvram_daemon exits, so it would not have
#     been a usable barrier even if the dependency had been real.
#
#   * The driver.ready half was the only start point, which is what made it
#     dangerous. Removing `disabled` removes the single point of failure.
#
# The one real hazard is /dev/wmtWifi: wmt_chrdev_wifi.ko registers the char
# device but UEVENTD creates the NODE asynchronously, and `exec ... insmod`
# returns before it exists -- measured 140 ms apart on the current build.
# stat() on a missing node is the only fast-exit path wlan_assistant has. With
# the service un-disabled and non-oneshot, init restarts it, and its own
# access() poll loop covers the gap. Nothing here needs to wait on it.
on property:vendor.connsys.driver.ready=yes
    exec u:r:vendor_modprobe:s0 -- /vendor/bin/insmod /vendor/lib/modules/wmt_chrdev_wifi.ko
    exec u:r:vendor_modprobe:s0 -- /vendor/bin/insmod /vendor/lib/modules/wlan_drv_${ro.vendor.wlan.gen}.ko
    exec u:r:vendor_modprobe:s0 -- /vendor/bin/insmod /vendor/lib/modules/bt_drv.ko
    exec u:r:vendor_modprobe:s0 -- /vendor/bin/insmod /vendor/lib/modules/gps_drv.ko

#
# wlan_assistant pushes the factory WIFI record from
# /mnt/vendor/nvdata/APCFG/APRDEB/WIFI into the WLAN driver through
# /dev/wmtWifi. That record carries the MAC and the 5 GHz band-enable and
# power tables; without it the driver takes a random MAC, loses the whole

#

# This signaling is necessary to prevent logging boot metrics after a runtime
# restart (e.g., adb shell stop && adb shell start).  /proc/uptime is not reset
# during a runtime restart, which leads to false boot time metrics being reported.
#
# The 'on boot' event occurs once per hard boot (device power on), which
# switches the flag on. If the device performs a runtime restart, the flag is
# switched off and cannot be switched on until the device hard boots again.

    # debugfs, and it has to be mounted HERE -- before `late-init`.
    #
    # Two things need it. /d/wakeup_sources, without which BatteryStats retries
    # every sample and emits a system_server wtf/DropBox write; and the whole of
    # /system/etc/init/atrace.rc, which chmods ~90 tracefs files including
    # `chmod 0222 /sys/kernel/debug/tracing/trace_marker`.
    #
    # atrace.rc declares those chmods in `on late-init`, and init.rc's own
    # `on late-init` only QUEUES early-fs/fs/post-fs/late-fs. ActionManager
    # drains current_executing_actions_ before it pops the next event
    # (action_manager.cpp ExecuteOneCommand), so every `on late-init` action
    # runs to completion BEFORE `on post-fs` starts. Mounting debugfs in
    # `on post-fs` therefore left every one of those chmods failing against an
    # unmounted directory, and trace_marker stayed at the kernel's 0220.
    #
    # That is not cosmetic. libcutils opens trace_marker at process start and
    # keeps the fd; webview_zygote must REOPEN it by path in each forked child,
    # as an unprivileged uid, and 0220 makes that EACCES -- which ART turns into
    # `JNI FatalError ... Failed open(/sys/kernel/debug/tracing/trace_marker)`
    # and aborts the child. Every sandboxed renderer died on this: measured 4
    # forks, 4 tombstones, a 100% failure rate, i.e. no web content anywhere on
    # the device. It also produced 242 `cutils-trace: Error opening trace file`
    # lines from processes that degrade gracefully instead of aborting.
    #
    # The cost of mounting this early is that AOSP's init.rc:374
    # `restorecon --recursive --cross-filesystems /sys/kernel/debug`, in ITS
    # `on post-fs`, now walks a live filesystem: 11046 inodes, 73 ms warm,
    # against ro.boottime.init=941. The walk sets nothing -- debugfs and tracefs
    # are labelled by genfscon, not by xattrs -- so it is pure cost, and it is
    # the right trade against a broken WebView. Do not "optimise" it back to
    # post-fs.
    #
    # It also cannot move any later for a second, independent reason: init.rc's
    # `on late-fs` does `chmod 0755 /sys/kernel/debug/tracing` and is queued
    # ahead of any vendor `on late-fs`.

    # ---- keypad suspend fix -------------------------------------------------
    #
    # This is the fix for the stuck Volume Up.
    #
    # MTK's kpd driver disables the whole keypad block across suspend:
    #     kpd_pdrv_suspend()  -> kpd_wakeup_src_setting(0) -> mt_reg_sync_writew(0, KP_EN)
    # while the keypad IRQ is EDGE-triggered (this board's DTB has
    # interrupts = <0 0xa4 2>, GIC_SPI 164 IRQ_TYPE_EDGE_FALLING) and the
    # driver's idea of which keys are down is a pure software shadow,
    # kpd_keymap_state[], written only from kpd_keymap_handler() and never
    # re-synchronised on resume. So a key transition that happens inside the
    # suspend window is lost permanently: the shadow still says "Volume Up is
    # down", the input core reports only transitions, and further presses of a
    # key it believes is already down produce nothing.
    #
    # From there the visible symptoms follow: PhoneWindowManager latches
    # mA11yShortcutChordVolumeUpKeyTriggered on a VOLUME_UP down with no
    # matching up, folds it into mPowerKeyHandled, and never calls
    # wakeUpFromPowerKey() - the power button stops lighting the screen.  Held
    # long enough from there, the PMIC's own long-press reset fires, which is
    # the occasional reboot.  It reproduces on the Stock ROM because the driver
    # is the same.
    #
    # kpd_call_state is MTK's own escape hatch, meant for "a call is ringing,
    # do not kill the keypad".  With it set to 2 BOTH kpd_pdrv_suspend() and
    # kpd_pdrv_resume() skip kpd_wakeup_src_setting() entirely, KP_EN stays 1
    # across suspend, no edge is ever lost and no shadow ever goes stale.  This
    # is also what mainline does - drivers/input/keyboard/mt6779-keypad.c has no
    # PM callbacks at all and simply never disables the block.  call_status is
    # referenced nowhere else in the driver except this attribute's show/store,
    # so there is no other behaviour riding on it.
    #
    # Cost: the keypad scanner keeps running off the 32 kHz clock in suspend,
    # which is microamps.
    #
    # Consequence worth knowing: with KP_EN left on, WAKE_SRC_R12_KP_IRQ_B is in
    # the default SPM suspend mask, so the volume keys become a real wake
    # source.  LineageOS's "volume buttons wake device" should therefore work
    # after this change - it could not before, at any configuration, and the
    # tree documented it as impossible.  Re-test it; the framework still gates
    # it on LineageSettings VOLUME_WAKE_SCREEN, which is off by default.
    #
    # The node is a driver attribute, root:root 0644, generic sysfs label.
    # vendor_init already holds { sysfs_type -sysfs_usermodehelper }:file
    # rw_file_perms from system/sepolicy/public/vendor_init.te:167, so this
    # needs no new type and no new rule.
    write /sys/bus/platform/drivers/mtk-kpd/kpd_call_state 2

    # ---- interactive governor ----------------------------------------------
    #
    # This kernel exposes ONE global tunable set at
    # /sys/devices/system/cpu/cpufreq/interactive/, shared by both policies, so
    # every value below has to be sane for a 156000-1001000 cluster and a
    # 286000-1508000 one at the same time.
    #
    # As shipped by the kernel this governor is unusually lazy for a part this
    # slow: go_hispeed_load 99 means it will not jump to hispeed_freq until a
    # CPU is essentially saturated, and target_loads 90 means it aims to leave
    # only 10% headroom. On 8xA53 that is the difference between a scroll that
    # starts at 1.5 GHz and one that spends its first two sample periods at
    # 598 MHz.
    #
    # Left at their existing values because they are already right:
    #   timer_rate 20000        20 ms sampling; halving it doubles governor
    #                           wakeups for a barely measurable gain
    #   min_sample_time 80000   how long a raised frequency is held. Lowering
    #                           this makes the governor drop back sooner, which
    #                           is the opposite of what is wanted here
    #   timer_slack 80000, boostpulse_duration 80000
    write /sys/devices/system/cpu/cpufreq/interactive/hispeed_freq 1508000
    write /sys/devices/system/cpu/cpufreq/interactive/go_hispeed_load 85
    write /sys/devices/system/cpu/cpufreq/interactive/above_hispeed_delay 20000
    write /sys/devices/system/cpu/cpufreq/interactive/target_loads "70 663000:75 1027000:85"

    # on a ~150 MB/s eMMC, downclocks, and is then at the bottom of the table
    # exactly when the data arrives.

    # ---- block I/O ----------------------------------------------------------
    #
    # Measured on the handset, 600 concurrent 4 KiB direct reads issued by four
    # readers while a 192 MiB fsync'd write ran alongside:
    #     cfq       378 ms
    #     deadline  271 ms   (-28%)
    #     noop      257 ms   (-32%)
    # Single-threaded the three are indistinguishable (~750 ms for 400 reads),
    # which is why this has to be measured under concurrency to see anything.
    # deadline is taken rather than noop: the extra 14 ms is inside the noise,
    # and noop has no read-vs-write starvation protection at all, which is the
    # one guarantee that matters while dexopt or an app install is writing.
    # deadline's own knobs were measured too and made no difference

    # defaults rather than being tuned on a guess.

    # cache of pages that were never slower than a memcpy.
    write /sys/block/zram0/queue/read_ahead_kb 0

# Stock persistent properties survive a partition flash in /data/property, and
# init applies them after the build.prop defaults. Re-assert the device-owned
# IMS capability contract once they load; the user-owned WFC switch is the
# deliberate exception below.
#
# This block used to live in a device init.mt6755.rc installed into the boot
# ramdisk. On this switch-root device that file is discarded before second-stage
# init runs, so it never executed. /vendor/etc/init/hw/init.${ro.hardware}.rc is
# imported by AOSP's /init.rc and is the correct home for it.
#
# TWO of these are ePDG BUILD flags with WFC-sounding names, and both must be 1
# or VoLTE cannot register. Neither is a user-facing WiFi-calling switch:
#
#   persist.vendor.mtk_wfc_support      -> isEpdgSupport() == mtkGetFeature(6);
#       gates 36 sites in mtk-ril.so including responseUnsolDataCallRspToMal,
#       the only caller of mal_datamngr_set_data_call_info (E-087).
#   persist.vendor.wfc.sys_wfc_support  -> the second gate inside queryEpdgRat
#       (mtk-ril.so 0x950bc); at 0 it logs "EPDG is not supported" and returns
#       eran_type 0, MAL's IMSM then logs "rat error!!" and spins forever on
#       imsm_handler.c:4141, and +CIREGU never leaves 0 (E-091).
#
# Both derivations are in vendor.prop. Do not restore either flag to 0: both
# VoLTE and the shipped VoWiFi path require them (HANDOFF trap 25).
#
# persist.vendor.mtk.wfc.enable is NOT re-asserted here, and it is the ONE
# deliberate exception to this block's rule that every persist.* key in
# vendor.prop is guarded against a stale /data. It is a USER SETTING -- the
# Wi-Fi calling switch in Settings -- so /data winning is the entire point.
# vendor.prop still carries it at 0, which is the value used when /data has
# none, i.e. WFC off until the owner turns it on.
#
# It USED to be re-asserted to 0 here, and that was a shipped bug once VoWiFi
# was enabled. Measured on the handset with WFC on and Wi-Fi associated:
#
#   09:33:07  init: setprop persist.vendor.mtk.wfc.enable 0   (this block)
#   09:33:20  WfoService: WfoService new WifiOffloadService
#   09:33:20  WifiOffloadService: isWfcEnabledByAnyPhone(), isOn:false
#
# The flashed image reads the bitmask only during construction, so toggling WFC
# there still needs a reboot. The current tree fixes the next image in
# extract-files.sh: its IMS_FEATURE_CHANGED receiver refreshes the properties
# and enqueues WFO's normal profile update without the invalid MtkImsManager
# cast (WI-055). Keep this init block from overwriting the user value.
on property:ro.persistent_properties.ready=true
    setprop persist.vendor.ims_support 1
    setprop persist.vendor.mims_support 1
    setprop persist.vendor.mtk_dynamic_ims_switch 1
    setprop persist.vendor.mtk_wfc_support 1
    setprop persist.vendor.vilte_support 0
    setprop persist.vendor.mtk.vilte.enable 0
    setprop persist.vendor.viwifi_support 0
    setprop persist.vendor.mtk.viwifi.enable 0
    setprop persist.vendor.mtk.ims.video.enable 0
    setprop persist.vendor.mtk_rcs_ua_support 0
    setprop persist.vendor.mtk_rtt_support 0
    setprop persist.vendor.volte_support 1
    setprop persist.vendor.wfc.sys_wfc_support 1
    # These three were missing from the list above, which is the one place the
    # contract is enforced against a stale /data.
    # persist.vendor.mtk.volte.enable is the MTK feature flag and is already
    # present in /data/property/persistent_properties, i.e. a vendor blob has
    # written it at least once, so it is exactly the class of key this block
    # exists for; its WFC sibling was listed and it was not.
    #
    # These persist.dbg.*_ovr keys are NOT redundant with the 0 that
    # PRODUCT_SYSTEM_DEFAULT_PROPERTIES puts in /system/etc/prop.default. On a
    # fresh device they are inert -- ImsManager tests == 1 and treats unset and
    # 0 alike -- but prop.default is loaded FIRST, so a persisted 1 left in
    # /data would silently win. ImsManager checks the per-phone WFC names before
    # the general name, so all three must be restated. This preserves the no-VT
    # and real-WFC/carrier-gate contract across a dirty /data.
    # persist.dbg.volte_avail_ovr
    # is gone from both places: VoLTE availability now comes from the filtered
    # CarrierConfig overlay, visible to every reader of the carrier key rather
    # than only isVolteEnabledByPlatform().
    #
    # The four persist.dbg.* keys below resolve to plat default_prop through
    # plat_property_contexts' `*` catch-all, and vendor_init may set them only
    # because this product leaves PRODUCT_COMPATIBLE_PROPERTY false
    # (PRODUCT_SHIPPING_API_LEVEL 26, which is stock's real
    # ro.product.first_api_level and must not be raised). If it were ever
    # raised above 27, public/domain.te:527-537 compiles
    # `neverallow { domain -init } default_prop:property_service set`, and this
    # block becomes a build failure rather than a silent regression. That is
    # the correct failure mode; do not pre-empt it by labelling platform-
    # namespace properties from a vendor property_contexts.

# and put read-ahead back to the default. Stock releases the frequency pin here
# too; it does not release read-ahead.

    write /proc/ppm/policy/userlimit_min_cpu_freq "1 -1"
    write /proc/ppm/policy/userlimit_min_cpu_core "0 -1"
    write /proc/ppm/policy/userlimit_min_cpu_core "1 -1"
    write /sys/block/mmcblk0/queue/read_ahead_kb 128

    # expansion with a default.
    #
    # Under FDE /data was dm-0: a separate gendisk with its own request queue
    # and its own backing-dev-info, which the writes above never reached. The
    # elevator choice carried over (dm is bio-based and remaps onto mmcblk0's
    # queue) but nr_requests and read-ahead did not, and /data is where dexopt
    # output and every app live.
    #
    # Unencrypted, /data mounts straight off mmcblk0p30, and then
    # dev.mnt.blk.data is NOT SET AT ALL: mount_handler.cpp:77-85 strips a
    # partition suffix only for sd*, then stats /sys/block/<value>/queue and
    # blanks the value when that is not a directory -- and /sys/block holds
    # gendisks, not partitions, so /sys/block/mmcblk0p30 does not exist. Live
    # on this handset: `getprop | grep dev.mnt` returns dev.mnt.blk.data and
    # nothing for /cache, which mounts the same way. An unset property is a
    # hard command failure, not a skip (util.cpp:344-348), so without the
    # default these three writes are three logged errors and three lost
    # tunings on every boot.
    #
    # ${name:-default} is supported at util.cpp:328-332. mmcblk0 is the correct
    # fallback: an unencrypted /data IS mmcblk0's queue, a partition has no
    # queue of its own, and the write is then idempotent with the one above.
    # /sys/block covers both -- it holds dm-0 as well as mmcblk0.
    write /sys/block/${dev.mnt.blk.data:-mmcblk0}/queue/read_ahead_kb 128
    write /sys/block/${dev.mnt.blk.data:-mmcblk0}/queue/nr_requests 256
    write /sys/block/${dev.mnt.blk.data:-mmcblk0}/queue/iostats 0

# so it cannot compete with the boot-time cluster pin above, which it would
# otherwise release the first time it saw the panel dark during boot.
#
# See device/xsh/k50sv1_64_bsp/perfd/k50sv1_perfd.c for why a daemon is needed
# at all -- the short version is that the PowerHAL's INTERACTION lock lasts
# 235-705 ms rather than the 5 s it is configured for, and that no PPM policy
# can be released by screen-off, so the screen-state edge has to come from
# userspace. That file also carries the removal recipe -- six sites, not the
# three this comment used to imply.
# Release the pin if the daemon ever stops. init's `stop` is SIGKILL
# (system/core/init/service.cpp), so the daemon cannot clean up after itself
# with a signal handler -- and without this, stopping it while the panel is lit
# leaves perfserv_perf_idx at maximum FOREVER. Reproduced on the handset: stop
# the service with the screen on, blank the panel, and 18 s later
# perfserv_perf_idx is still 5616 with all eight cores online. That is the worst
# possible state for battery, produced by trying to turn the feature off.
#
# `stopped` does NOT cover a crash, and an earlier version of this comment said
# it did. Service::Reap() publishes "stopped" only under
# flags_ & (SVC_DISABLED | SVC_RESET) (system/core/init/service.cpp:376); a
# non-oneshot, non-disabled service that dies falls through to :411 and
# publishes "restarting", then "running". So a crash never fires this trigger.
# Nothing is lost by that: `pinned` starts at -1 in the daemon, so the restarted
# process re-applies the pin on its first tick rather than the trigger releasing
# it. The trigger exists for the deliberate `stop` case above, which is the one
# that would otherwise leave the pin latched forever.
#
# vendor_init already holds proc_mtk_power_ppm:file write
# (sepolicy/vendor/vendor_init.te:70), so this needs no new rule.
on property:init.svc.vendor.k50sv1_perfd=stopped

# ---- power-off charging -------------------------------------------------
#
# There was NO class charger service anywhere in the image: not in this file,
# not in /system/etc/init, not in AOSP's own init.rc, which only does
# `class_start charger`. system/core/healthd/Android.mk builds /system/bin/charger
# with no LOCAL_INIT_RC, unlike the two Soong modules beside it, so AOSP supplies
# the binary and expects the device to supply the service. Stock had all three
# pieces (kpoc_charger.rc, an `on charger` block, and a usb one) and this port
# dropped every one.
#
# The consequence: plug a charger into a powered-OFF handset and MTK's LK boots
# the normal boot image with androidboot.mode=charger; init.cpp then queues ONLY
# the `charger` trigger -- no fs, no post-fs-data, no framework -- and nothing
# starts. Black screen, no battery UI. And because system_suspend is `class
# core` and never runs, nothing ever suspends, so the SoC idles at full draw for
# the entire charge.
#
# No new sepolicy: init->charger:process transition and
# charger:charger_exec:file entrypoint are both already in the platform policy,
# and public/charger.te grants everything the binary touches.
#
# UNTESTED -- it cannot be tested over adb. Verify by powering the handset fully
# off and inserting the cable: the battery animation should appear, a power-key
# press should boot Android, and the SoC should suspend between screen updates.
# `on init`, not `on charger`, and that is a correctness fix rather than a
# preference. ImportParser::EndFile() (import_parser.cpp:47-53) parses imports
# only after the importing file is fully parsed, and ActionManager queues
# matching actions in insertion order (action_manager.cpp:56-66), so AOSP's own
# `class_start charger` (system/core/rootdir/init.rc:777-778) runs BEFORE
# anything an imported vendor file puts in `on charger`. These chowns were
# racing the process they exist to serve. In charger mode init queues only
# early-init, init and charger, and wait_for_coldboot_done runs before `on
# init`, so `on init` is both early enough and safe in a normal boot.
on init
    # The MTK SPM node stock hands over in the same block, so the low-power
    # path has an owner while the framework is absent.
    chown system system /dev/spm
    chmod 0660 /dev/spm
    # No chown of /sys/power/state or /sys/power/wakeup_count here, and the
    # stated reason for once having them was wrong twice over.
    #
    # Right half: libsuspend hard-selects the wakeup_count implementation
    # (system/core/libsuspend/autosuspend.c:35), which opens /sys/power/state
    # and /sys/power/wakeup_count (autosuspend_wakeup_count.cpp:52-53) and
    # never touches /sys/power/autosleep. Stock's autosleep chown IS dead and
    # is correctly not carried over.
    #
    # Wrong half: "wakeup_count staying root-owned made autosuspend_enable()
    # fail". It never does. AOSP's own init.rc:292-293 chowns BOTH nodes to
    # system:system, and that is in `on init`, which init queues in charger
    # mode too (init.cpp:821-827 queues early-init, init, charger). These two
    # lines only ever restated a grant that was already in place.
    # No `chmod 0666 /dev/kmsg` here. device.mk already condemns stock for
    # world-writing the kernel log to buy back a log line, and it is redundant
    # besides: the service declares `file /dev/kmsg w` below, init opens that fd
    # as root before dropping to `user system`, and klog.cpp:39-43 finds it
    # through android_get_control_file() before ever trying open() by path.

# The SPM PCM firmware, which off-mode charging needs and never got.
#
# The chowns above hand /dev/spm to system, exactly as stock does, but stock's
# `on charger` (factory_image_unpacked/vendor/etc/init/hw/init.mt6755.rc:62-65)
# does one more thing in the same breath: `start spm_script`. That service is
# `class core` + `oneshot` (vendor/etc/init/spm_script.rc, shipped by
# proprietary-files.txt:209-210), and `class_start core` lives in AOSP's
# `on boot` (system/core/rootdir/init.rc:768). Charger mode never queues
# `on boot` -- init.cpp:821-827 queues early-init, init and charger and stops --
# so /vendor/bin/spm_loader was never executed with the cable in and the
# handset off, and sepolicy/safety/spm_loader.te:6 says what that costs:
# "Opening /dev/spm read-only asks the kernel driver to load its PCM firmware."
#
# Without that firmware the SoC cannot enter its deep suspend state, which is
# precisely what BoardConfig.mk's BOARD_CHARGER_ENABLE_SUSPEND was turned on
# to obtain. The permission half of the fix shipped and the actuation half did
# not.
#
# This must be its own `on charger` and not be folded into `on init`. A oneshot
# started from `on init` would run again at `class_start core` on every normal
# boot (Service::Start() only short-circuits on SVC_RUNNING, which a completed
# oneshot does not have), loading the firmware twice. `on charger` runs only in
# charger mode, where nothing else starts it.
#
# Ordering against AOSP's own `class_start charger` is fine and is not the
# race the chown block above was written to fix: init.rc:777-778 is queued
# first, so charger is forked before this oneshot, but charger's first
# request_suspend(true) is seconds into its idle path, well after a oneshot
# that only opens a device node has exited.
on charger
    start spm_script

service charger /system/bin/charger
    class charger
    seclabel u:r:charger:s0
    user system
    group system graphics input wakelock
    # SYS_BOOT only. BLOCK_SUSPEND guards /sys/power/wake_lock, and Q's
    # libsuspend charger path never opens it -- autosuspend_wakeup_count.cpp
    # uses /sys/power/state and /sys/power/wakeup_count, which are plain DAC.
    # system/sepolicy/public/charger.te:14-15 grants sys_tty_config and
    # sys_boot and NOT block_suspend, so asking for it would be an AVC under
    # Tier 2 in exchange for nothing. The `wakelock` supplementary group stays:
    # that one is DAC on /sys/power/wake_lock (radio:wakelock 0660) and costs
    # no capability.
    capabilities SYS_BOOT
    file /dev/kmsg w
