4. Closed dead end: MAL RDS is blocked, and it cannot be unblocked from here
----------------------------------------------------------------------------
Every ~5 s, MediaTek's radio-domain-selection module refuses to send its IMS
control AT commands:

  MAL-RDS: (ru_ims_ctrl_send_atcmd, 1587) [RDS-W][RU] MDmngr(1) or Epdgs(0) is not ready
  MAL-RDS: (ru_check_imsrat,        8837) [RDS-W][RU] MDmngr(1) or Epdgs(0) is not ready

libmal_rds.so holds the AT strings AT+EIMSVOLTE=%d, AT+EIMSVOICE=%d,
AT+EIMSREGCON=0,%d, AT+EIMSCCP=%d, AT+EIMSDEREG=4. The gate is a plain AND of
two context bytes at the top of the sender (fcn @ 0xdbef8):

  0xdbf64  ldr r0, [r0, 0xac8]   ; MDmngr ready
  0xdbf6c  beq -> log "not ready"
  0xdbf74  ldr r0, [r0, 0xacc]   ; Epdgs ready
  0xdbf7c  bne -> proceed

and 0xacc has exactly ONE writer in the whole library:

  0xe939c  movw r0, 1
  0xe93a4  str  r0, [r1, 0xacc]

inside the handler for EVENT_MFI_RU_SET_UIPARAM_REQ, whose logged parameters
are fgimsolte_en, fgwfc_en, rdspolicy, omacp_fqdn, roam, fgwifiui_en,
fgimsccp_en, fgallow_turnoff_ims, wifioff_reason. Those are Wi-Fi-calling UI
settings, i.e. they come DOWN from the framework.

Measured attempt to satisfy it, on the running handset (/vendor remounted rw,
reverted afterwards):
  - pushed vendor/lib{,64}/libmal_epdga.so, vendor/lib{,64}/libwo.so,
    vendor/bin/epdg_wod, vendor/etc/init/init.wod.rc
  - persist.vendor.mtk_wfc_support=1  -> mtkmal reads this as EPDG_SUPPORT
    (mtkmal fcn 0x4840: md_prop_ver >= 1 selects persist.vendor.mtk_wfc_support,
    otherwise persist.mtk_epdg_support), and the module then loads:
      MAL-Daemon: (main, 461) load /vendor/lib/libmal_epdga.so
      MAL-Daemon: (main, 485) load symbol epdga_entity_init
  - persist.vendor.mtk_epdg_support=1 -> epdg_wod stops exiting with
      [epdg_wo]: [DMN] NOT support WI-FI OFFLOADING, stopping WI-FI OFFLOAD DAEMON
    and stays running.

Result after both: Epdgs is STILL 0, and libmal_epdga.so emits no log line at
all. The missing piece is the framework end:

  ImsService: can't get WifiOffloadService
  ImsService: checkAndBindWifiOffloadService: sWifiOffloadService = null
  ImsService: No MwiService exist

com.mediatek.ims looks up ServiceManager.getService(WifiOffloadManager.WFO_SERVICE)
and falls back to MwisConstants.MWI_SERVICE; neither is registered here. The
implementation is com.mediatek.wfo.impl.WifiOffloadService in
mediatek-wfo-legacy.jar, which this port does not ship and which needs
MediaTek's SystemServer additions to start. Without it, ImsService's
onRequestImsSwitch() -- the ONLY caller of turnOnIms/turnOffIms besides the
one-shot initImsAvailability at construction -- is never invoked, and RDS's
Epdgs flag is never set.

Conclusion: shipping libmal_epdga.so, libwo.so and epdg_wod is necessary but
NOT sufficient, so none of them is shipped. Do not re-add them expecting VoLTE
to change. This block is also NOT proven to be the reason IMS does not
register: mtk-ril.so sends its own AT+EIMSVOLTE=1 at init
("volte setting is enable and AT+EIMSVOLTE=1 is sent"), independently of RDS.

5. One real parity gap, repaired
--------------------------------
persist.vendor.mtk_dynamic_ims_switch was 0; stock sets 1. With it not "1",
ImsConfigManager.updateImsResrouceCapability() takes its short branch and never
calls IMtkImsConfig.setImsResCapability(), so the RIL is never asked to
re-push per-MCCMNC IMS configuration to the modem. Measured with 0:

  ImsConfigManager: updateImsServiceConfig after SIM event, phoneId:0

and nothing else. Measured with 1:

  ImsConfigManager: DYNAMIC_IMS_SWITCH_TRIGGER phoneId:0, simState:LOADED
  ImsConfigManager: get MtkImsConfigImpl of phone 0
  ImsConfigManager: Set res capability: volte = 1, vilte = 0, wfc = 0
  ImsConfigManager: DYNAMIC_IMS_SWITCH_COMPLETE phoneId:0, simState:LOADED

+CIREGU stayed 0, so this is parity repair, not the fix.

6. Constraint that decides where a test SIM goes
------------------------------------------------
  ImsService: getMainCapabilityPhoneId: mainPhoneId = 0
  RIL-IMS  : imsInit - multi ims not support, rid change to 0

ImsCommonUtil.supportMims() is false on this build, so ImsService calls
initImsAvailability for the main-capability phone only, and that is phone 0.
A VoLTE test SIM in slot 1 can never register. Any WI-029 measurement must put
the test SIM in slot 0.
