E-088 artifact: the USB-C headset is an ANALOG accessory, the kernel detects it,
and two device-tree omissions stop Android from routing to it
================================================================================

Fixture: owner's USB-C earphone physically inserted. Because the handset has one
USB-C port, USB adb is unavailable while it is; this was captured over network
adb at 192.168.1.251:5555 on the E-084 Tier-1 image.

1. It is not a USB audio device
--------------------------------
  # cat /proc/asound/cards
   0 [mtsndcard      ]: mt-snd-card - mt-snd-card
                        mt-snd-card

One card, the internal one, with the headset inserted. No UAC card appears and
/sys/kernel/debug/usb/devices lists no audio device. So the headset is wired to
the internal codec through the Type-C analog mux -- USB-C analog audio accessory
mode -- and to Android it is an ordinary WIRED headset, not a USB one.

2. The kernel detects it, correctly, with a microphone
-------------------------------------------------------
  # getevent -p /dev/input/event0
    name:     "ACCDET"
    events:
      KEY (0001): 0072  0073  00a4  0246
      SW  (0005): 0002* 0004* 0006  0007*

The asterisk is the current state. Set: SW_HEADPHONE_INSERT (0x02),
SW_MICROPHONE_INSERT (0x04), SW_JACK_PHYSICAL_INSERT (0x07). Clear:
SW_LINEOUT_INSERT (0x06). /proc/bus/input/devices reports B: SW=d4, i.e. the
same four switches supported.

InputReader agrees:

  # dumpsys input
    Device 2: ACCDET
      Switch Input Mapper:
        SwitchValues: 94

That field is printed with %x (SwitchInputMapper::dump), so it is 0x94 =
(1<<2)|(1<<4)|(1<<7) -- exactly the three switches above. The framework's input
stack has the headset.

3. The framework nevertheless routes to the speaker
-----------------------------------------------------
  # dumpsys audio
     Devices: speaker
     Devices: earpiece
     Devices: speaker

No wired headset anywhere in the connected-device state, and no
"wired/A2DP/hearing aid device connection" event for it.

4. First omission: the switch path is gated off
------------------------------------------------
WiredAccessoryManager has three sources and this build has none of them live:

  - /sys/class/switch/h2w -- absent on this kernel (legacy switch class)
  - extcon                -- absent
  - EV_SW on an input device -- present, but forwarded only when
    config_useDevInputEventForAudioJack is true
    (WiredAccessoryManager.java:107-108 reads it, :115-130 consumes the
    switches at boot, InputManagerService.java:1864 forwards them at runtime)

AOSP defaults that resource false (config.xml:2612) and the device overlay did
not raise it. MediaTek's own BSP raises it, in
device/mediatek/common/overlay/accdet/.../config.xml.

The device tree previously asserted the opposite, in keylayout/ACCDET.kl:
"DO NOT set it true on this chassis. Confirmed live: dumpsys input reports
SwitchValues: 0". That check was run with nothing in the port. It measured an
empty port, not absent hardware.

5. Second omission: there is nowhere to route it either
--------------------------------------------------------
configs/audio_policy_configuration.xml declared only these output devices:

  AUDIO_DEVICE_OUT_BLUETOOTH_SCO{,_CARKIT,_HEADSET}
  AUDIO_DEVICE_OUT_EARPIECE
  AUDIO_DEVICE_OUT_SPEAKER
  AUDIO_DEVICE_OUT_TELEPHONY_TX

No AUDIO_DEVICE_OUT_WIRED_HEADSET, no AUDIO_DEVICE_OUT_WIRED_HEADPHONE, no
AUDIO_DEVICE_IN_WIRED_HEADSET. Stock declares all three, with identical profiles
(PCM_32/16, 44100/48000, stereo out; PCM_16, 8k-48k, mono/stereo in).

So even with the switch path enabled, AudioPolicyManager would have had no sink
for the headset. Both omissions had to be fixed; either alone is inert.

The MTK HAL already implements the paths: the shipped vendor/etc/audio_device.xml
carries headphone_output, headphoneSpeaker_output, headset_mic_input and
Headset_Speaker_Amp_Switch.

6. Why the symptom is "both at once" rather than "silence"
-----------------------------------------------------------
With the policy selecting AUDIO_DEVICE_OUT_SPEAKER, MediaTek's HAL opens and
keeps the speaker path, while the codec's headphone output is live because the
analog mux is closed and the ACCDET/codec path is powered on insertion
independently of Android's routing decision. Nothing ever asks the HAL to close
the speaker, because as far as AudioPolicyManager is concerned nothing changed.

7. The policy half is proven live
-----------------------------------
The corrected configs/audio_policy_configuration.xml was pushed to
/vendor/etc/audio_policy_configuration.xml and audioserver restarted. It came
back healthy and registered the new ports:

  # dumpsys media.audio_policy
      - tag name: Wired Headset
      - type: AUDIO_DEVICE_OUT_WIRED_HEADSET
      - tag name: Wired Headphones
      - type: AUDIO_DEVICE_OUT_WIRED_HEADPHONE
      - tag name: Wired Headset Mic
      - type: AUDIO_DEVICE_IN_WIRED_HEADSET

The overlay half needs a build; it is one boolean and its only consumer is the
gate quoted in section 4.

8. Not yet done
----------------
End-to-end confirmation that plugging the headset now mutes the speaker requires
the built image. The inline-remote keys (KEY_VOLUMEUP/DOWN/PLAYPAUSE/
VOICECOMMAND on the same ACCDET ADC) stay neutralised in ACCDET.kl: the
stuck-VOLUME_UP fault of E-024/E-028 was diagnosed on the assumption that the
comparator had nothing attached, and that premise is now also gone, so
restoring them needs its own measurement with a headset present.
