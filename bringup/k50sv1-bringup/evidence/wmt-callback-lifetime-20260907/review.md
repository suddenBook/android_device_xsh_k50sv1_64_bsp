Independent review of the callback lifetime candidate

No high-confidence blocking finding was identified in the reviewed changes or in their composition with platform commit `b5920c2ae581ecdd6febcabe322f71504dfcebf2`. The exact source hashes and final commit binding are recorded in `review.json`. This was a read-only production review; only this evidence directory was written. No handset operation or full kernel build was performed.

The bridge reference covers the entire module callback. `wmt_platform_bridge_get` copies the table and increments `bridge_users` under the same IRQ-safe spinlock that withdrawal uses to clear the table. Once withdrawal releases that lock, new dispatches see the empty table. The decrement occurs in the builtin adapter after the indirect module call has returned. A callback paused at its final module return therefore still has a counted reference, even after every WMT operation reference has been released. Empty and partial tables return the existing fallback values without leaking references.

Registration and unregistration hold `bridge_update_lock` across withdrawal and the wait. A concurrent writer cannot publish another table while the preceding writer is draining. Dispatch releases the spinlock before invoking the callback, and the wait holds no spinlock. Nested dispatch retains the outer reference. Registration intentionally permits a new table after an earlier close has completed; this is not a permanent ban on future initialization.

The actual selected build uses the builtin `connadp` adapter and module `wmt_drv`; `wmt_plat_alps.c` is selected, and `wmt_plat_stub.c` is excluded. The only source registration path is `wmt_plat_init -> mtk_wcn_cmb_stub_reg -> wmt_export_platform_bridge_register`. The actual teardown path is module exit through `wmt_detect_driver_exit -> mtk_wcn_common_drv_exit -> WMT_exit`. Failed library initialization calls `wmt_lib_deinit` directly from the outer failure label. These callers run in a context that can sleep. No reviewed callback calls registration or unregistration. The local module loader releases `module_mutex` before calling the module exit function. The detect character device sets its cdev owner to `THIS_MODULE`, and the local `cdev_get`/`cdev_put` implementation pins that module for an open descriptor; ordinary unload cannot overlap an init ioctl through an already open descriptor.

The `WMT_exit` barrier is before the first resource teardown, including the temperature lock used after the last thermal operation. The `wmt_lib_deinit` barrier is before pool admission is closed, workers are stopped, or timers and locks are destroyed. Existing thermal work can therefore finish with its dependencies still available. This library barrier also runs when library initialization failed before platform ownership was recorded. The complete real thermal callback was inspected: it can perform three WMT operations and later update its static history under the temperature lock. Waiting only on operation references would not protect that final work or the final module return; the new outer barrier does.

With the platform commit composed in memory, `wmt_plat_deinit` unregisters the stub before hardware, mutex, and wake resource cleanup. The builtin update mutex is released before each unregister call returns, so the outer, library, and platform close calls are sequential rather than recursive lock acquisitions. The direct platform tests pause thermal, assertion, and clock callbacks individually at the module return and verify that resource cleanup remains at zero until release. Repeating platform cleanup produces no additional teardown.

Independent execution used a snapshot of the author's 19 source-derived cases and added three direct platform teardown cases. Full production bridge, stub dispatch, platform cleanup, outer/library cleanup, thermal callback, and clock entry functions are extracted without rewriting their production bodies. The two platform files are read from `b5920c2` in memory; no worktree was patched. Synchronization primitives, hardware, thermal command completion, assertion internals, and STEP actions are host adapters. Function instrumentation pauses the complete module wrapper at entry or immediately before its return.
